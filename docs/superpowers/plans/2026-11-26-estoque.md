# Estoque de insumos: plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Construir o módulo `estoque`: produtos, locais, livro de movimentos com saldo por produto × local × lote, custo médio, FEFO, baixas automáticas, inventário, NF-e pelo XML, voz e avisos.

**Architecture:**
- `movimento_estoque` é um livro imutável. `saldo_estoque` é atualizado na mesma transação, e só a `lancarMovimento` escreve nos dois.
- Aviário e notas chamam funções exportadas por `apps/api/src/modulos/estoque/index.ts`, dentro da transação deles. O estoque não importa de nenhum outro módulo.
- Os contratos ficam em `@vocare/shared` (`packages/shared/src/estoque/`).

**Tech Stack:** Hono, Drizzle/Postgres (Neon; PGlite nos testes), Zod, Next.js 16, Vitest. Dependência nova (autorizada): `fast-xml-parser`, só no `apps/api`.

**Spec:** `docs/superpowers/specs/2026-11-26-estoque-design.md`

**Ajustes em relação à spec**, porque o código mostrou isto:
- Vacina e tratamento de animal só são gravados pela aprovação da nota (`notas/regras/aplicar.ts`). Não há formulário para eles, então a baixa desses dois vai para a **fase 5** (voz). Na fase 2 ficam o registro diário e a vacinação de lote, que tem formulário.
- Registro diário e vacinação **não têm exclusão** hoje. O registro diário é gravado por `substituirApontamento` (tela) e `somarApontamento` (voz), e é único por galpão e dia. A baixa da ração acompanha esses dois caminhos (`sincronizarRacao`). Não existe caso de "apagar".
- Uma migration cria **todas** as tabelas novas na fase 1. Outra, na fase 2, acrescenta as colunas nas tabelas que já existem. Assim são só duas autorizações de escrita no banco.

## Global Constraints

- **Node 24** em todo comando: `export PATH="$HOME/.nvm/versions/node/v24.19.0/bin:$PATH"`.
- **Antes de mexer no `apps/web`, ler `apps/web/AGENTS.md`.** O Next 16 tem mudanças incompatíveis.
- **Camadas e imports:**
  - O web nunca importa do `apps/api`, nem o contrário. O contrato vai em `packages/shared`.
  - Fora do módulo, só se entra pelo `index.ts`; no web, também pelo `dados.ts`, nunca a partir de `"use client"`. Sem ciclo entre módulos.
  - Arquivo acima de ~300 linhas se divide pelo assunto.
- **Camadas da api:** `rotas/` (só HTTP), `regras/` (decide e grava; devolve `Resultado` de `src/base/resultado.ts`), `consultas/` (leituras). Erro de rota sai como `{ error: string }` com o status do `Resultado`. A rota confere o membro com `membroAtual(c.req.raw.headers, orgId)` e devolve 403 com `SEM_ACESSO`.
- **Permissão:** toda rota do estoque decide por `podeNoEstoque(papel, acao)` e nunca compara o papel direto. Hoje ela libera owner, admin e member.
- **Quem escreve no livro:** só `lancarMovimento` escreve em `movimento_estoque` e `saldo_estoque`. Movimento não tem rota de edição nem de exclusão.
- **Números:**
  - Quantidades em `numeric(14,3)`, custos em `numeric(14,4)`.
  - No JSON viajam como `number`. Na gravação, `String(arredondar(x, 3 ou 4))`; na leitura, `Number(...)`, como `areaM2` no aviário.
- **Identificadores e texto:**
  - Identificadores em português, como no resto do projeto.
  - Na tela é "nota", nunca "ocorrência".
  - Mensagens de erro em pt-BR.
- **Arquivos que não se tocam:** `apps/api/src/db/schema.ts` é gerado e não se edita.
- **Migrations:**
  - Geradas com `npx drizzle-kit generate --name <nome>` em `apps/api`, e ficam em `apps/api/drizzle/`.
  - Aplicar na homologação (`npm run db:migrate:hom -w apps/api`) **só com autorização do Arthur no chat, na hora**.
  - Nunca aplicar em produção neste plano.
- **Testes:**
  - Toda rota nova tem teste em `apps/api/test/estoque/`, cobrindo o caminho feliz e **outra organização** (`criarFazenda` duas vezes; a de fora leva 403 ou 404).
  - Função pura tem `x.test.ts` ao lado.
  - Tela (componente React) fica sem teste.
- **Commits:**
  - Um por fase, na branch `homologacao`, com `npm test` verde. Nunca incluir `.claude/launch.json`.
  - A mensagem segue o estilo `estoque: <o que mudou>`, em português, terminando com `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
  - O push é do Arthur.

## Review Focus

1. **Dois movimentos no mesmo saldo ao mesmo tempo:** o saldo final é a soma exata, sem perder nenhum. Teste na Task 3.
2. **Registro diário salvo de novo sem mudar a ração** (só corrigiu mortes): nenhum movimento novo. Se a voz soma mais ração no mesmo dia, sai só a diferença. Teste na Task 9.
3. **NF-e com um único `det`** (o parser devolve objeto, não lista) **e item com dois `rastro`**: é lido como 1 item com 2 lotes, que viram 2 movimentos. Teste na Task 12.
4. **Decimais:** 480,5 + 0,1 + 0,2 kg dá saldo `480.8`, sem resíduo de ponto flutuante. Teste na Task 3.
5. **Estornar uma entrada já consumida:** o saldo fica negativo, sai o aviso, e o custo médio é recalculado sem dividir por zero. Teste na Task 5.

### Task 3: núcleo do livro

**Files:**
- Create em `apps/api/src/modulos/estoque/regras/`:
  - `movimento.ts`: `lancarMovimento`, `sairPorFefo`, `estornarMovimento`;

  - `negativo.ts`: `avisarSaldoNegativo`.
- Create: `apps/api/test/estoque/movimento.test.ts`

**Interfaces:**
- Consumes: as tabelas da Task 2 e `novoCustoMedio`, `repartirFefo` e `arredondar` do `shared`.
- Produces:
  - `type Tx = Parameters<Parameters<typeof db.transaction>[0]>[0]`, no mesmo padrão de `aviario/regras/alojamento.ts`.
  - `type NovoMovimento = { orgId; userId: string | null; produtoId; localId; tipo: TipoMovimento; quantidade: number /* com sinal */; custoUnitario?: number; loteFabricacao?: string; validade?: string | null; data: string; origemTipo: OrigemMovimento; origemId?: string | null; grupoId?: string | null; estornaId?: string | null; motivo?: string | null; ocorrenciaId?: string | null }`.
  - `lancarMovimento(tx: Tx, m: NovoMovimento): Promise<{ id: string; saldoLocal: number }>`:
    - grava o movimento;
    - atualiza o saldo com `insert ... on conflict (produto_id, local_id, lote_fabricacao) do update set quantidade = saldo_estoque.quantidade + excluded.quantidade`;
    - quando `tipo === "entrada"` e a quantidade é positiva, atualiza `produto.custoMedio` com `novoCustoMedio`, usando o saldo total do produto **antes** do movimento;
    - em saída, quando `custoUnitario` não vem, usa o `custoMedio` atual.
  - `sairPorFefo(tx, a: Omit<NovoMovimento, "quantidade" | "loteFabricacao" | "validade" | "tipo"> & { quantidade: number /* positiva */; tipo?: "saida" | "ajuste"; loteFabricacao?: string }): Promise<string[]>`:
    - com `loteFabricacao` informado, sai só desse lote;
    - sem ele, lê os saldos do produto no local e chama `repartirFefo`;
    - a `sobra` vai para o lote `''`;
    - devolve os ids criados.
  - `estornarMovimento(tx, orgId, userId, movimentoId, motivo): Promise<Resultado<string[]>>`:
    - 404 se o movimento é de outra organização;
    - 409 com "Este movimento já foi estornado." ou "Estorno não se estorna.";
    - estorna também o par com o mesmo `grupoId`;
    - se o original era entrada, chama `recalcularCustoMedio`.
  - `recalcularCustoMedio(tx, produtoId): Promise<void>`: relê o livro do produto por `createdAt` e aplica `novoCustoMedio` só nas entradas não estornadas.
  - `podeNoEstoque(papel: Papel, acao: AcaoEstoque): boolean`: hoje devolve `true` para owner, admin e member.
  - `avisarSaldoNegativo(orgId, itens: { produtoId; localId }[]): Promise<void>`:
    - é chamada **depois** do commit;
    - lê os saldos e, para cada um < 0, chama `notificar(orgId, await administradores(orgId), { texto: "Saldo negativo: <produto> em <local>", detalhe: "Falta lançar uma entrada?", link: "/estoque" })`;
    - importa `notificar` e `administradores` de `../../avisos`, que é a única dependência do estoque.
